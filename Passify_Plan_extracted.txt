PassifyProject Development PlanSimple ID and Event Pass GeneratorVersion 1.0 | 23 September 20261. Project OverviewPassify is a web application for creating branded IDs and event passes, generating QR-based verification links, and managing pass status. When a visitor opens the website, the first screen asks how Passify will be used.The opening options are:Personal use: Create a pass for yourself or a small private activity.For an organization: Create and manage passes for employees, students, members, visitors, or event attendees.Both options use the same pass-generation, QR verification, and status-management system. The selection changes onboarding, dashboard labels, and organization features.2. Team StructureThe project is divided between four members. User Experience Flow3.1 Opening SelectionThe first screen should ask:How will you use Passify?Personal useFor an organizationSave the choice in the workspace record:workspace_type: "personal" | "organization"3.2 Personal Use FlowUser selects Personal use.User registers or logs in.User selects a pass template.User enters holder details and uploads a photo.User reviews the live preview.Passify generates a pass number and QR code.User downloads or prints the pass.Anyone can verify the pass through its public QR URL.3.3 Organization FlowUser selects For an organization.User registers or logs in.User creates an organization profile.User creates an event, department, or usage group.User creates one pass or imports multiple people using CSV.User searches, downloads, expires, or revokes passes.Verifiers check passes through the public QR verification page.4. Development PhasesPhase 1: Project SetupOwners: All membersCreate the Next.js and TypeScript project.Configure Git, coding standards, Supabase, and environments.Agree on the database schema and API contracts.Create the base application layout and design system.Phase 2: Authentication and Usage SelectionOwners: Members 1, 2, 3, and 4Build the personal/organization selection screen.Implement registration, login, logout, and protected routes.Create workspace records and save workspace type.Test routing to the correct dashboard.Phase 3: Personal Pass CreationOwners: Members 1, 2, and 3Build template selection, holder form, and live preview.Create pass APIs and validation.Add photo upload, QR generation, PNG download, and printing.Phase 4: Organization ManagementOwners: Members 1, 2, 3, and 4Build organization and event setup.Add dashboard, pass table, search, and filtering.Implement CSV import and ownership checks.Phase 5: Verification and Status ManagementOwners: Members 1, 2, 3, and 4Build the public verification route: /verify/[token].Implement token lookup and status calculation.Add revoke, expiry, and verification logging.Review publicly visible personal data.Phase 6: Templates and Export QualityOwners: Members 1, 2, 3, and 4Complete Event Badge, Employee ID, Visitor Pass, Student ID, and Membership Card templates.Test QR readability, print dimensions, and export quality.Phase 7: Final Testing and DeploymentOwners: All membersRun complete user journeys on desktop and mobile.Review accessibility, security, performance, and browser compatibility.Fix release-blocking issues and deploy the production application.5. Recommended TechnologyFrontend and backend: Next.js with TypeScript.UI: React with CSS or a small component library.Authentication: Supabase Auth.Database: Supabase PostgreSQL.File storage: Supabase Storage.QR codes: A maintained QR-code library.Deployment: Vercel or an equivalent Next.js host.Testing: Vitest, React Testing Library, and Playwright.7. Definition of DoneUsers choose personal or organization use when opening the website.The selected mode is saved to the correct workspace.Personal users can create, download, and print passes.Organization users can manage organizations and multiple passes.All five templates work with live previews and QR codes.Verification works without login and shows the correct status.Active, Expired, and Revoked states are handled correctly.Users cannot access another workspace's information.Image uploads, CSV imports, exports, and printing work correctly.The application works on desktop and mobile browsers.QA has completed the acceptance checklist.The application is deployed and documented.8. Team Working RulesMember 1 and Member 2 agree on API request and response shapes before frontend integration.Member 3 reviews authentication and authorization changes before deployment.Member 4 tests each completed feature before it is marked complete.All pull requests should include a short description and testing notes.No feature should be considered complete until it works on both desktop and mobile widths.
